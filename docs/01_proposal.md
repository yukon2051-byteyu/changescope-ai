# ChangeScope AI 企画提案書（v0.1 / 2026-11-01）

> 本書の表記ルール
> - **[確認済]** … 公式情報などで確認した事実（確認日：2026-11-01）
> - **[想定]** … 設計上の仮定・試算値。実測値ではない
> - **[未確認]** … Webで確認できなかった、または要追加調査の事項

---

## 0. コンセプト（v0.2 / 2026-11-02 改訂）

> **「変更の前に、まだ確認していないことを見つけるAI」**
>
> 変更によって何が起きるかを予測するだけでなく、**変更前に何を確認していないか**（未確認の連携・関係者・前提）を見つけ出し、「誰に・何を聞けばよいか」まで具体的に示す。
> 単なる変更管理システムではなく、ITコンサルタントの**ヒアリング力・課題発見力・リスク管理能力**をAIで再現する。

### 3つの柱

| 柱 | 内容 | AIと人の役割 |
|---|---|---|
| **① 依存関係を作る** | 既存のExcelや業務資料（業務フローの説明、システム一覧、規程の文章など）から、要素とつながりの**候補**を作る。候補には根拠となる資料の該当箇所を付ける | **AIが候補を作り、人が確認して登録する**（自動では登録しない） |
| **② 確認漏れを見つける（中核）** | 登録データと変更内容から、**確認していないこと**を具体的に指摘する。例：「給与システムとの連携が未確認です。人事担当者に確認してください」。そのまま使える質問文（ヒアリング項目）も出す | 登録データにもとづく指摘か、**AIの推測**かを必ず分けて表示する |
| **③ 変更案を比べる** | 変更案AとBで、影響範囲・リスク・**未確認事項**がどう変わるかを並べて示す（Aだけ・Bだけ・両方に出る影響） | 費用・期間など不明な数値は作らず「要見積もり」とする |

### 変えない原則
- **AIは候補と指摘を出す。決めるのは人。**
- 確実な処理（グラフ探索・ルール判定）はPython、あいまいな処理（資料の読み取り・確認漏れの推測・質問文の作成）だけAI。AIが止まっても、AIを使わない分析は動く。
- AIの出力は「登録情報で確認できた事項／AIの推測／情報不足で未確認の事項」に分けて表示する。

### 進め方（v0.2）
| 順番 | 内容 |
|---|---|
| 1 | AIを呼び出す土台（費用の上限・エラー時の処理） |
| 2 | **② 確認漏れを見つけるAI**（中核）。部門別の調整ポイント・トラブル予測・見落としがちな費用・推奨する進め方・未登録の影響の推測を含む。4シナリオの事前生成サンプル（サンプルであることを明示）も作る |
| 3 | 図で入力する画面（試作済み）＋ **① 資料からの依存関係の抽出** |
| 4 | **③ 変更案A・Bの比較**と可視化、PDFレポート |

以下の1章以降は v0.1（2026-11-01）の内容。コンセプトと進め方は本節を優先する。

## 1. 企画概要

| 項目 | 内容 |
|---|---|
| 名称 | ChangeScope AI（仮称） |
| 一言で | 「何かを変えたい」と入力すると、登録された組織情報の依存関係から影響範囲・リスク・確認事項・対応計画を提示する変更影響分析ツール |
| 解決する課題 | 変更時の影響調査が担当者の経験と記憶（属人的な知識）に頼っており、関係部署・データ移行・切り戻し手順などの**確認漏れ**が導入後のトラブルにつながる |
| 利用者 | 社内SE、ITコンサル、DX推進、PM/PMO、BPR担当、業務部門責任者（業種不問） |
| 入力 | ①変更内容（自由文）②組織・業務・システム情報と依存関係（CSV／サンプル）③追加ヒアリングへの回答 ④変更案A・B |
| 出力 | 影響範囲（直接・間接）、影響マップ、リスク一覧、関係者確認リスト、テスト・対応計画、変更案比較、PDF報告書 |
| 基本方針 | **確実な部分はPython（グラフ探索・ルール判定）、あいまいな部分だけAI**。AIの出力は「登録情報で確認済み／AI推測／未確認」に必ず分類する |

### AI-BICとの役割分担

| | AI-BIC（既存） | ChangeScope AI（本件） |
|---|---|---|
| 問い | 何を改善すべきか | その変更をすると、どこに影響が出るか |
| 分析の主役 | AIによるヒアリング・提案 | **登録データのグラフ探索**＋AIによる補完 |
| 根拠 | AIの推論 | 依存関係データ（根拠・確認状態つき） |
| 将来連携 | AI-BICの改善提案 → ChangeScopeで影響評価（MVP対象外） | |

## 2. 競合製品・既存サービスとの差別化

### 2.1 調査結果

| 製品・手段 | 概要 | 状態 |
|---|---|---|
| ServiceNow（Change Management / Analyze Impact） | CMDB（IT構成情報のデータベース）の依存関係を探索し、そのトポロジーをLLMに渡して影響度・信頼度・理由を返すAIワークフローを提供。探索ノード数に上限（既定250）あり | [確認済] 公式ドキュメント |
| Virima、Ivanti、Jira Service Management など ITSMツール | ITSMと連携した変更影響分析を提供 | [確認済] ベンダー記事レベル。機能詳細は[未確認] |
| エンタープライズアーキテクチャ（EA）管理ツール（例：LeanIX 等） | アプリ・業務能力の関係を管理 | [未確認] 今回Web確認せず、一般知識に基づく |
| 汎用生成AI（ChatGPT、Claude等）への直接相談 | 手軽だが、自社の依存関係を知らないため一般論になる | [想定] |
| Excelの影響調査表・チェックリスト | 多くの企業の現実的な手段 | [想定] |

**注目点：** 大手のServiceNowも「依存関係のグラフ探索 → その結果をLLMに渡して評価」という構成を採っています。本件の設計方針（Pythonで探索、AIで評価）は業界の方向性と一致しており、面接で設計の妥当性を説明する材料になります。

### 2.2 差別化案

| 観点 | 既存ITSM・CMDB型 | ChangeScope AI |
|---|---|---|
| 対象範囲 | 主にIT構成要素（サーバー、アプリ等） | **業務プロセス・部門・役割・帳票・社内規程**まで同じモデルで扱う |
| 導入の重さ | CMDB整備が前提、エンタープライズ価格 | CSV数枚で始められる軽量構成 |
| 根拠の扱い | AIの信頼度スコア | 3区分（登録情報で確認済／AI推測／未確認）＋依存関係ごとの根拠・確認状態 |
| 見落とし検出 | 主に構成要素の影響 | 関係者未登録、データ移行・切り戻し未検討など「確認されていない事項」を検出 |
| 意思決定支援 | 変更要求の承認フロー中心 | 変更案A・Bの比較、未確定値は「要見積もり」と明示 |

**正直な位置付け：** 商用製品の代替ではなく、「中小〜中堅企業やプロジェクト初期の影響調査を、軽量に・根拠つきで行う」ことを狙ったポートフォリオです。

## 5. 共通データモデル

### 5.1 考え方
業種ごとに専用の表を作らず、**「要素（ノード）」と「依存関係（エッジ）」の2種類だけ**で表現します。
- ノード：点。業務・システム・部門など
- エッジ：点と点を結ぶ線。「AはBにデータを渡す」など

これにより、製造業でも小売業でも同じ仕組みで分析できます。

### 5.2 要素（elements）

| 項目 | 型 | 必須 | 説明 |
|---|---|---|---|
| element_id | 文字列 | ○ | 例：SYS-001 |
| name | 文字列 | ○ | 例：勤怠管理システム |
| element_type | 区分 | ○ | process / system / department / role / data / document / external_service / rule |
| description | 文字列 | | 概要 |
| owner | 文字列 | | 責任部門・役割（要素IDまたは名称） |
| aliases | 文字列 | | 別名（「勤怠システム」「タイムカード」など、入力文との照合に使用） |

| element_type | 日本語 | 例 |
|---|---|---|
| process | 業務プロセス | 月次給与計算、経費精算 |
| system | 情報システム | 勤怠管理システム、会計システム |
| department | 部門 | 人事部、経理部 |
| role | 担当者・役割 | 給与担当、承認者（課長） |
| data | データ | 勤怠実績データ、顧客マスタ |
| document | 帳票 | 給与明細、月次売上報告書 |
| external_service | 外部サービス | クラウドストレージ、銀行振込サービス |
| rule | 社内規程・ルール | 就業規則、経費規程、職務権限規程 |

### 5.3 依存関係（dependencies）

| 項目 | 型 | 必須 | 説明 |
|---|---|---|---|
| dependency_id | 文字列 | ○ | 例：DEP-001 |
| from_id | 文字列 | ○ | 影響の発生元 |
| to_id | 文字列 | ○ | 影響を受ける側 |
| relation_type | 区分 | ○ | 下表 |
| direction | 区分 | ○ | one_way（from→toのみ伝わる）/ both（双方向に伝わる） |
| evidence | 文字列 | ○ | 根拠（例：「2026年度 業務フロー図 p.3」「人事部ヒアリング」） |
| status | 区分 | ○ | confirmed（確認済）/ unconfirmed（未確認）/ assumed（推定） |
| note | 文字列 | | 補足 |

| relation_type | 意味 | 例 |
|---|---|---|
| provides_data | データを提供する | 勤怠管理システム → 勤怠実績データ |
| uses | 利用する | 勤怠実績データ → 月次給与計算 |
| integrates_with | システム連携する | 勤怠管理システム ⇄ 給与計算システム |
| performs | 業務を担当する | 月次給与計算 → 人事部（業務が変わると担当部門に影響） |
| approves | 承認する | 経費精算 → 承認者（課長） |
| governed_by | 規程に従う | 勤怠管理 → 就業規則 |
| produces | 帳票を作成する | 給与計算システム → 給与明細 |
| depends_on | その他の依存 | 汎用 |

**方向の約束：** エッジは常に「from が変わると to に影響しうる」向きで登録します。CSV作成者が迷わないよう、テンプレートに例を記載します。

### 5.4 分析結果・運用データ

| テーブル | 主な項目 | 保存先 |
|---|---|---|
| analyses（分析） | 入力文、確定した変更対象、ヒアリング回答、作成日時 | セッション内のみ（後述） |
| impacts（影響） | 要素ID、影響区分（direct/indirect）、段数、経路（依存関係IDの並び） | セッション内のみ |
| risks（リスク） | 観点、影響内容、発生条件、推奨対策、確認事項、**区分（registered / ai_inferred / unknown）**、根拠の依存関係ID | セッション内のみ |
| options（変更案） | 案名、6観点の値（未確定は null → 画面で「要見積もり」） | セッション内のみ |
| api_usage（API利用記録） | 日時、利用者キー（ハッシュ化）、モデル、入出力トークン、推定費用、成否 | 永続DB |

│   ・サンプルデータ：リポジトリ内CSV（読み取り専用）                         │

### 6.1 技術選定と理由

| 用途 | 選定 | 理由 |
|---|---|---|
| 言語 | Python 3.12 | 手元は3.15だが、出たばかりで一部ライブラリ未対応の恐れ [想定]。Streamlit Cloudでも選択可能な安定版を使う |
| UI | Streamlit | AI-BICで経験あり。Pythonだけで画面が作れる |
| グラフ解析 | NetworkX | Pythonの定番グラフライブラリ。循環検出・経路探索が標準機能 |
| 影響マップ | pyvis | NetworkXのグラフをそのままインタラクティブな図にできる。クリック連動は不可のため、詳細表示は一覧選択で代替 |
| PDF | fpdf2 | 純Python・依存が少ない。日本語フォント（Noto Sans JP、SIL OFLライセンス）を同梱 |
| AI | Anthropic公式SDK + Claude Haiku 5.5 | 低価格。構造化出力（JSON形式を強制）で結果を機械的に検証できる |
| テスト | pytest | 標準的。AI部分はモック（偽物の応答）でテストし、費用ゼロ |
| 永続DB | ローカル：SQLite／公開版：外部DB無料枠（Supabase等を候補） | Streamlit Cloudのファイルは再起動で消える（一般に知られた仕様だが公式記述は [未確認]）ため、利用回数記録だけ外部に置く |

**利用者データを永続保存しない理由：** ログイン機能なしで複数人が使うため、保存すると他人のデータが混ざる危険があります。MVPでは「ブラウザを閉じたら消える」方式にし、PDFで持ち帰ってもらいます。これがセキュリティ要件（データ混在防止）への最も簡単で確実な対応です。

## 7. AI分析の具体的な処理フロー

AI呼び出しは**1分析あたり最大3回**。それ以外はPythonで処理します。

| # | 処理 | 担当 | 内容 |
|---|---|---|---|
| 1 | 入力チェック | Python | 文字数（1,000字）・禁止パターン確認、利用回数・予算の残り確認（cost_guard） |
| 2 | 変更対象の候補抽出 | Python | 入力文と要素名・別名を照合し候補を出す（AI不要・無料） |
| 3 | **変更内容の整理＋確認質問** | **AI #1** | 入力文＋候補要素一覧 → 変更対象・目的・想定範囲・不足情報の質問（最大5問）をJSONで返す |
| 4 | 変更対象の確定・回答 | 利用者 | AIの提案をそのまま採用せず、人が対象を確定（人による確認） |
| 5 | 影響探索 | Python | 幅優先探索（近い順に広げていく探索）で影響要素と経路を抽出。1段目＝直接、2段目以降＝間接（最大段数は設定値、初期3） |
| 6 | 見落とし検出 | Python | 汎用ルール：影響範囲にdataがあるのに移行の検討がない／departmentに対応するroleが未登録／status=unconfirmedの依存関係を経由している 等 |
| 7 | **リスク分析・関係者・テスト計画** | **AI #2** | 変更概要＋探索結果（要約済み）＋見落とし結果 → 9観点のリスク、関係者確認リスト、7項目の計画をJSONで返す。**根拠とした依存関係IDの記載を必須にする** |
| 8 | AI出力の検証・区分付け | Python | ①JSON形式チェック ②記載された依存関係IDが実在するか照合 → 実在：「登録情報で確認済」、なし／不一致：「AI推測」、AIが「情報不足」としたもの：「未確認」 |
| 9 | **変更案比較**（任意） | **AI #3** | A案・B案の説明＋各案の影響範囲（Pythonで算出）→ 6観点比較。費用・期間は入力がなければ必ず null とさせ、画面で「要見積もり」表示 |
| 10 | 表示・PDF | Python | 3区分を色・アイコンで区別して表示、PDF化 |

### 7.1 エラー時の動き
- タイムアウト・API障害・予算超過 → AI部分を飛ばし、手順5・6（Pythonの結果）だけで結果を表示し、「AI分析は利用できませんでした」と明示
- JSON形式不正 → 1回だけ再試行、だめならAIなし結果
- **デモモード**：手順3・7・9の代わりに、事前に用意したサンプル結果（JSON）を読み込む。画面とPDFに「サンプル結果（AIによるリアルタイム分析ではありません）」と表示

#### 8.3.1 モデルの変更（2026-11-03 決定）
4シナリオを Haiku 5.5・Sonnet 5.5・Opus 5.5 で実際に分析して比べた結果、上位モデルの方が確認漏れの指摘が明らかに具体的だった（例：CSV連携の文字コード・コード体系、SLA・データ返却条件、補う統制、電子帳簿保存法）。「AIの質はこのシステムの肝」という判断で、**3,000円の上限を超えることも許容**し、次の構成に変更した。

| 使う場所 | モデル | 1回あたり（実測ベースの試算） | 月あたり |
|---|---|---|---|
| アクセスコードでのAI分析 | Claude Opus 5.5（入力$4／出力$20） | 約21円 | 月150回で約3,140円 |
| 事前生成のサンプル（4シナリオ） | Claude Opus 5.5（入力$4／出力$20） | 約21円 | 作るときだけ（4シナリオで約84円） |

当初は分析を Sonnet 5.5（1回約9円）にする案だったが、利用者の判断で Opus 5.5 にそろえた。アプリ側の月の予算は25ドル（約4,000円）に変更し、Claude Console の上限も同じ額に合わせる。比較にかかった費用は合計約119円（試算）。

### 8.4 費用を守る仕組み（二重の安全装置）
1. **アプリ側**（実装）：利用者ごと月3回、月間150回、月間予算$25（2026-11-03 に$5から変更）、入力1,000字、max_tokens上限、予算の90%到達でAI機能停止
2. **API提供側**（設定を案内）：Claude Consoleで月間利用上限（spend limit）を設定。アプリにバグがあっても請求額を止められる。**アプリ側の制御だけでは請求上限は保証されません**

### 8.5 Claude Code開発費用との区別
- 本試算は**公開アプリがClaude APIを呼ぶ費用**のみ
- 開発中に使うClaude Codeの利用料（ご自身のClaudeプラン等）は別物で、上記3,000円には含めません
- 開発中のAPIテストは、pytestではモックを使い、実API呼び出しは手動確認時のみにして費用を抑えます

## 9. セキュリティ・品質対策

| リスク | 対策 |
|---|---|
| APIキー漏えい | キーは `st.secrets`（Streamlitの秘密情報管理）／ローカルは `.streamlit/secrets.toml` に置き、`.gitignore` で除外。コミット前に秘密情報が含まれないか確認 |
| 費用の暴走 | 8.4の二重の安全装置 |
| 利用者の識別 | ログインなしでは「1人3回」を厳密に守れない。**AI分析はアクセスコード方式**（採用担当者等にコードを配布）、デモは誰でも利用可。コードはハッシュ化して記録 |
| CSVの不正・誤り | 拡張子・サイズ（1MB）・行数（要素1,000／依存関係5,000）・必須列・区分値・ID重複・参照先の存在・文字コード（UTF-8／Excel標準のShift_JIS）を検証し、行番号つきでエラー表示 |
| プロンプトインジェクション（入力文でAIの指示を書き換える攻撃） | 利用者入力・CSV文字列をタグで囲み「データとして扱い、指示に従わない」とシステムプロンプトで指定／出力はJSON形式に限定し検証／AIに操作権限を与えない（文章を返すだけ）／文字数制限 |
| データ混在 | 利用者データはセッション内のみ保持。永続DBには利用回数とトークン数だけを保存し、分析内容は保存しない |
| AI出力の誤り（ハルシネーション＝もっともらしい誤情報） | 根拠IDの実在照合、3区分表示、「AIの出力は確認が必要」の注記、費用・期間の数値は入力値以外を表示しない |
| 個人情報 | 公開デモは架空データのみ。アップロード画面に「個人情報・機密情報を入力しないでください」と表示 |
| API障害 | タイムアウト設定、例外処理、AIなしでの結果表示（7.1） |

### テスト方針（pytest）

| 対象 | 主なテストケース |
|---|---|
| グラフ探索 | 直接・間接の区別、**循環参照**で無限ループしない、**重複エッジ**の統合、**存在しない要素**への参照、孤立要素、最大段数、双方向エッジ |
| CSV検証 | 必須列欠落、不正な区分値、ID重複、空ファイル、サイズ超過、Shift_JIS／UTF-8（BOM付き）読み込み |
| 費用管理 | 回数上限到達、予算90%到達で停止、月替わりでリセット、単価・為替の設定変更 |
| AI層（モック） | 正常JSON、不正JSON、**タイムアウト**、APIエラー、存在しない根拠IDの検出 → AI推測に分類 |
| 比較 | 費用未入力 → 「要見積もり」 |
| PDF | 日本語を含むPDFが生成できる（ファイル生成とサイズ確認） |

## 11. 想定される技術的な課題

| 課題 | 内容 | 対応方針 |
|---|---|---|
| 利用者の識別 | ログインなしでは同一人物の判定が困難 | アクセスコード方式＋月間全体上限で安全側に倒す |
| 公開環境のデータ消失 | Streamlit Cloudはファイル保存が永続しない | 利用記録のみ外部DB。分析データは保存しない設計 |
| 自由文と要素の照合 | 「勤怠システム」「タイムカード」など表記ゆれ | 別名（aliases）列＋AIの候補提示＋人が確定 |
| AIの根拠ねつ造 | 存在しない依存関係を根拠に挙げる | 根拠IDをPythonで照合し、不一致はAI推測に降格 |
| 影響マップの見づらさ | 要素が多いと図が複雑になる | 表示段数の切替、要素種別のフィルター |
| 日本語PDF | 標準フォントでは文字化けする | 日本語フォントを同梱 |
| ExcelのCSV | Shift_JIS保存が多い | 文字コード自動判定 |
| Pythonのバージョン | 3.15はライブラリ未対応の恐れ | 3.12で仮想環境を作成 |
| AIの品質と費用 | Haikuで分析品質が十分か | Phase 2で4シナリオを実際に試し評価。不足ならプロンプト改善→モデル変更の順で検討 |
| ServiceNowとの類似 | 構成が似ていると言われる可能性 | 対象範囲（業務・規程まで）と3区分・軽量性を差別化として明確に説明 |

## 12. 採用担当者に訴求できるポイント

1. **業務課題起点の企画力**：「変更時の確認漏れ」という多くの企業に共通する課題を、変更管理の考え方で整理した
2. **AIの使いどころを設計した判断力**：確実な処理はPython、あいまいな処理はAIに分担。AIが止まっても業務が止まらない構成
3. **根拠の追跡性**：「なぜこの部門に影響するか」を依存関係の経路と根拠資料で説明できる。AIの推測と事実を分けて提示
4. **汎用データモデル設計**：8種類の要素と依存関係だけで業種を問わず表現
5. **コスト管理の実務感覚**：公式料金に基づく試算、アプリ側と提供側の二重の上限、月約220円（想定）の運用
6. **セキュリティ・品質への配慮**：秘密情報管理、入力検証、データ混在防止、異常系を含む自動テスト
7. **業界動向との整合**：大手ITSM製品も「依存関係探索＋LLM評価」を採用しており、方向性の妥当性を説明できる
8. **3つの既存ポートフォリオとのストーリー**：集計（データ処理）→ 資産管理（データ管理）→ AI-BIC（改善提案）→ ChangeScope（変更影響評価）と、業務改善の一連の流れをカバー
